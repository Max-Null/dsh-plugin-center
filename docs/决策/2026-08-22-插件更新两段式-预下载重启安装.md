# 2026-08-22 · 插件更新两段式：预下载到临时目录 + 重启时安装

> 变更为「三段式」（见文末演进节）：先直装，撞锁再进特殊路径。

## 背景

SSiD 内嵌 DSH（Electron 主进程 boot `ssid` profile）。插件市场更新
`dsh-better-sidebar@0.15.1` 时反复失败：

```
[ERR_PNPM_EPERM] rename node_modules\node-pty_tmp_* -> node_modules\node-pty
```

实测结论（2026-08-22，用 rename 探测 + 移走旧目录重装实验钉死）：

- `node-pty` 的 `conpty.node`（Windows 原生二进制）**被正运行的思灵进程加载**，
  Windows 禁止覆盖已加载的原生模块（目录 rename 可以、文件替换不行）；
- 目标目录已存在时，pnpm 的 `rename tmp -> 目标` 又受 Windows 目录语义限制；
- 因此**运行中更新原生模块必然失败**，此前只能"退出思灵 → 装 → 再开"。

而纯 JS 插件更新、启停插件（写 patch 文件）都无此问题——前者只是"文件到位 +
重启生效"，后者就是两段式（写配置 → 重启时 loader 读取）。

## 决策：与"禁用插件"同款两段式

1. **点击更新（现在）**：只做**预下载**——`pnpm pack <name>@<version>
   --pack-destination ~/.ssid/pending-plugin-updates/`（不动 node_modules，
   无锁；网络/版本问题此刻暴露），并把条目写入
   `~/.ssid/pending-plugin-updates/index.json`；
   UI 立即返回并显示「待重启生效」（复用禁用插件的 pending tag 语义）。
2. **重启（SSiD 启动、boot DSH 之前）**：`kernel.ts` 消费清单，逐个
   `pnpm add -w <name>@<version>`（精确版本，沿用 8/18 的
   minimumReleaseAge 精确版本策略；store 已缓存 → 秒装，此时无任何锁）。
   成功 → 移除条目、删 tgz；失败 → 保留条目与日志，下次启动重试；
   任何失败都不阻断 boot。
3. **新装（install）不改**：目标目录不存在时 rename 无冲突，不需两段式。
4. 消费逻辑放 `shell/kernel.ts`（安装版需重新打包归档生效；源码版即时）。

## 实现要点

- `dsh-plugin-center/src/update.ts`：新增 `preparePluginUpdate()`（pack +
  writePendingUpdates）+ `readPendingUpdates/writePendingUpdates/pendingUpdateDir`；
  `PnpmResult` 增加可选 `pending: boolean`（client 文案区分）。
- `dsh-plugin-center/src/engine.ts`：`update()` 改调 `preparePluginUpdate`
  （仍走 enqueuePnpm 串行链，防 pnpm 并发）。
- client：更新成功 toast 改为「已下载更新，重启思灵后自动安装」+ 条目
  显示「待重启生效」tag（pendingInstall 机制）。
- `seek-soul-in-darkness/shell/kernel.ts`：boot 前 `applyPendingPluginUpdates()`
  （自含 pnpm 候选/超时/日志，独立于插件中心进程）。
- 涉及文件：`dsh-plugin-center/src/{update,engine}.ts`、
  `dsh-plugin-center/client/index.tsx`（build 后 client.js）、
  `seek-soul-in-darkness/shell/kernel.ts`。

## 验证

- 插件 `npm run build`（tsc + client）+ shell `tsc --noEmit`
- 手动 `pnpm pack dsh-better-sidebar@0.15.1 --pack-destination <tmp>` 确认
  tgz 命名（scope 包名规则）后再写死路径
- boot-smoke：写入测试 pending（一个可装、一个故意不存在）→ boot →
  断言可装项被消费移除、失败项保留、boot 不阻断
- 端到端：插件市场点更新 → 「待重启生效」→ 重启思灵 → 版本已更新

## 演进：三段式（2026-08-22 第二轮，用户拍板）

用户问题："有的插件能直接更新成功"。扫 profile 原生二进制佐证：仅 4 个原生包
（sharp/koffi/node-addon-require-builtin/node-pty），DSH 实际加载的只有
node-pty——**失败不是插件特性，而是"撞上被加载的原生模块"**：
纯 JS 包（Node 读完即释放句柄）与目标不存在的新包、未被加载的原生模块都可
随时直装成功。

因此两段式改为**三段式（直装优先 + 撞锁分流）**：

1. **先直装**（`updatePlugin`，pnpm add）：绝大多数（纯 JS/未锁原生/新增包）
   直接成功 → 返回 `direct: true`，UI toast「已更新，重启后生效」；
2. **直装失败且为文件锁**（detail 匹配 EPERM/EBUSY/rename）→ 分流：
   - **SSiD**（kernel 声明 `SSID_PENDING_CONSUMER=1`，有 boot 前消费方）→
     转两段式：`preparePluginUpdate` 预下载（npm pack）→ pending 清单 →
     UI「待重启生效」+ **统一弹窗「立即重启 / 稍后重启」**（多更新全部
     ready 后弹一次；立即重启走 `/ssid/api/sessionRoot.restart`，复用
     进行中会话 busy 保护）；
   - **官方 dsh web / 无消费方** → 仿社区市场（chnjames/dsh-plugin-market
     等）：返回 `command`（`dsh plugin --profile <p> add <name>@<ver>`），
     UI 弹**指令复制弹窗**（提示先关闭应用再在终端执行），不在进程内直装。
3. **非锁失败**（网络/版本）→ 原样报错（客户端更新失败 toast）。

实现差异：`PnpmResult` 增加 `direct?: boolean`；`engine.update()` 三段逻辑；
`rpc.ts` value 透传 `direct/pending/command`；client 三分支处理
（直接/待重启弹窗/指令弹窗）。
