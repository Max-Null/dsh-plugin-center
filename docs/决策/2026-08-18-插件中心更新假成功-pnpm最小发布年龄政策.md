# 插件中心更新假成功：pnpm 11 minimumReleaseAge 政策拦截

> 决策日期：2026-08-18 · 状态：已实施修复（待重启验证）· 影响面：@max-null/dsh-plugin-center

## 现象

Web GUI 插件中心点「更新」后 toast 显示「已更新，重启 dsh web 后生效」（或偶尔「更新失败」），
重启后版本不变，插件中心再次提示有更新；反复多次无效。

## 诊断过程（全部可复现的证据链）

1. 更新链路：浏览器 → RPC `/plugin-center/update` → host 侧
   `runPnpm(['add', '-w', <name>], profileDir)` → 在 `C:\Users\MaxNull\.dsh\profiles\web`
   目录 spawn pnpm，`stdio: 'inherit'`，以 exit code 判定成败。
2. 直接从外部 POST `http://127.0.0.1:3080/plugin-center/update`（DSH connection RPC 四象限消息）
   在 **DSH web 进程内部**复现：返回 `ok: true`，但 node_modules、package.json、lockfile 全都没变。
   —— 证实是"假成功"，不是进程环境/沙箱问题。
3. 隔离实验（临时目录）确认 pnpm 行为：
   - `pnpm add -w <name>`（不带版本）→ latest 0.13.0 被拦 → 版本不动或只升到次新，exit 0；
   - `pnpm add -w <name>@latest` → 同样 "Already up to date"，exit 0；
   - `pnpm add -w <name>@0.13.0`（精确版本）→ 真正安装，pnpm 自动把该包写入
     pnpm-workspace.yaml 的 `minimumReleaseAgeExclude`。
4. pnpm 11 的 supply-chain 政策 `minimumReleaseAge`：发布不满 N 分钟的新版本被解析器拒绝。
   （`pnpm.mjs` 内 `runAgeCheck`：发布时间晚于 cutoff 即 violation；默认值未显式设置时
   行为上拦截了 08-17 发布而放过 08-16 发布的版本，量级 ~24h。）
   CLI 无对应 flag（`--minimum-release-age` 是 unknown option），只能经 pnpm-workspace.yaml 配置。

## 根因

插件中心 update 命令 `pnpm add -w <name>` **不带版本**。pnpm 11 引入 minimumReleaseAge 后，
latest 若发布不足政策年龄，解析器静默回退（不升级、exit 0），插件中心以 exit code 判定成功
→ 假成功 → 用户重启后版本没变，循环重试。

## 决策

**update 命令携带精确目标版本：`pnpm add -w <name>@<toVersion>`**。
`checkUpdates` 已经拿到了 `toVersion`，一路传到 RPC 和引擎即可。精确版本触发 pnpm 自身
的排除机制（自动写入 `minimumReleaseAgeExclude`），语义明确且不需要改用户 profile 的
pnpm-workspace.yaml。

不改 profile 配置（`minimumReleaseAge: 0` 仅作为用户侧兜底选项记入文档，不主动写入）。

## 实施

- `src/update.ts`：`updatePlugin(name, profileDir, version?)`，version 存在时拼 `name@version`。
- `src/engine.ts`：`update(name, version?)`。
- `src/rpc.ts`：update endpoint 读取 `{ name, version? }`。
- `client/index.tsx`：`updateOne(name, toVersion)` / `updateAll` / WhatsNew 的 `updateNow`
  全部携带 `version: u.toVersion`。

## 验证

- 复现命令在 DSH 进程内假成功（版本不动）→ 修复后同一 spawn 路径（shell:true + inherit）
  精确版本 add 真实升级：dsh-better-sidebar 0.12.2→0.13.0、dsh-excel-panel 0.3.2→0.6.1、
  dsh-sidebar-qa 0.1.0→0.2.0，均 exit 0，pnpm 自动写入 minimumReleaseAgeExclude。
- dsh-skin 保持 file: 本地链接未动（更新会替换为 registry 版、断开发链接——待用户决定）。
- 新 dist 需重启 dsh web 才加载；重启后插件中心 UI 的「更新」即携带精确版本。

## 遗留观察

- `dsh-excel-panel@0.6.1` 与 `dsh-sidebar-qa@0.2.0` 的 peer 要求 `dsh-better-sidebar: ^0.12.0`，
  与 0.13.0 范围冲突（pnpm 仅警告）。发布时序上 0.6.1/0.2.0 早于 0.13.0，peer 范围未跟进；
  先升级再观察运行时表现，必要时向两包作者提 peer 范围更新。
- `dsh-skin` 原为 `file:` 链接（本地开发），更新后已替换为 registry `0.4.1` 精确保存
  （pnpm 对原 file: 依赖替换时的保存行为）。恢复本地开发链接需手动
  `pnpm add -w "dsh-skin@file:H:/MaxNull/WorkStation/dsh-skin"`。

## 第二轮修复（重启后发现 dsh-skin 仍提示更新、点击报「更新失败」）

两个叠加原因：

1. **浏览器跑旧 bundle**：重启 dsh web 不会刷新页面内已加载的 client.js。旧 client
   调 `update` 不带 version，新 host 端校验直接拒绝 → toast「更新失败：
   update: version is required」。刷新页面即自愈（DSH boot 图的 `?rev=` hash 保证
   新 bundle 被拉取）。
2. **`meta.ts` 的 `packageCache` 进程级缓存永不失效**：pnpm 更新 node_modules 成功后，
   `listInstalled` 仍返回进程启动时的旧版本 → checkUpdates 永远提示更新、点更新永远
   "Already up to date" 假成功循环。修复：导出 `clearPackageCache()`，在
   `enqueuePnpm` 每次 install/update 落盘后清空（与 installedNamesCache/updatesCache 一起失效）。

dsh-skin 已真实更新到 0.4.1（node_modules/package.json/lockfile 验证）。
